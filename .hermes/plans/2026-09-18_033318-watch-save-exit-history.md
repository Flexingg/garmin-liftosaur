## Diagnosis (already done — do not re-derive, and do not "fix" anything else about it)

### 1. The 422 is a broken percent-encoder on the watch

`Comms.urlEncode()` (introduced in commit `d084048`, "Fix the save crash for real (no POST body)")
escapes reserved characters with `ch.toNumber()` on a **1-character String**:

```monkeyc
var code = ch.toNumber();            // "/".toNumber()  -> null   ("5".toNumber() -> 5)
var v = (code == null) ? 0 : code;   // -> 0
out += "%" + hex(...v...) ;          // -> "%00"  = a NUL byte
```

So every `|`, `;` and `/` in the workout payload is transmitted as `%00`. The live backend log for the
user's actual save attempts shows it (journalctl for `garmin-liftosaur-backend.service`):

```
POST /api/v1/watch/workout?payload=Day%203%00Week%201%005%003%001%20BBB%20-%20Squat%00Bench%00Deadlift%00OHP%00...
                                                                        ^^^^ all separators are NUL
... HTTP/1.1" 422 Unprocessable Entity
```

`watch_api.parse_compact()` splits the payload on `|` and `;`; with NULs it finds one header field
(`len(fields) < 4`) and raises `422 malformed payload header`. The same file's **previous** build
posted correctly (`...Day%202%7CWeek%202%7C5%2F3%2F1%20BBB... HTTP/1.1" 200 OK` at 15:39:58), so this
is a regression from that commit, not a design flaw in the query-string approach.

Secondary consequence: `Comms.onPostResponse()` treats the 422 as retryable and stashes the payload;
`WorkoutController._pendingBody` is **never cleared**, so once anything has been retried, every later
`postWorkout()` re-sends the stale stashed workout and the new one is silently never uploaded.

### 2. "Done" is a sentinel leaking into the UI

`WorkoutController.currentExerciseName()` returns the literal string `"done"` when the cursor has run
past the last exercise. That string is then used as the *title* of the info / history / stats screens
and is even fetched from the backend — the server log proves it:

```
GET /api/v1/watch/exercise?name=done HTTP/1.1" 200 OK
```

which returns `{"exercise":"done","last":null,"recent":[]}` → a screen titled "done" with empty stats.

### 3. The app has no exit

- `SetDelegate.onBack()` opens `AdjustView` unconditionally, so after the workout is finished BACK
  shows a junk "edit set" screen for a non-existent set instead of leaving.
- `WorkoutController.resolveSave()` clears the saved cursor but leaves `_exIndex` past the end, and the
  finish `Menu2` is the only thing popped → the user lands back on the "DONE" screen. Pressing the top
  button calls `finishWorkout()` again. There is no path to the day picker and none out of the app.
- `ActivityRecording` sessions were stopped before this, so "discard" also gives no activity, which
  matches the report "discarding a workout just pushes me back into the workout".

### 4. Bundled data-correctness bugs found while diagnosing (fix these too — same code paths)

- **Garbage duration.** `System.getTimer()` is milliseconds since *boot*, and `restore()` sets
  `_started = true` without restoring `_sessionMs` (stays 0). A session restored after an app restart
  therefore reports `elapsedMs()/1000` = device uptime. The real log shows `duration: 27138s` (7.5 h)
  in a payload for a ~45 min workout. That number is written into the Liftosaur record.
- **Wrong `week` / `dayInWeek`.** `buildWorkoutBody()` hardcodes `:week => 1` and uses
  `_dayIndex + 1` for `:day_in_week`. Since commit `eb92e28` the day list contains **all four weeks**,
  so a Week-3 day is sent as `week: 1, dayInWeek: 15`. The record lands in the wrong week/day.
- **Stale retry stash.** The 422-era stash stored on the watch would be re-posted on the next launch
  *dated today* with the 7.5 h duration. Discard it by versioning the storage key (Task 3).

## Task 1 — Rewrite the percent-encoder (this is the 422 fix)

**File:** `embedded/monkeyc/source/Comms.mc` — replace the whole `urlEncode` function.

RFC 3986: only `A-Z a-z 0-9 - . _ ~` pass through; everything else becomes `%XX`. The code point must
come from a **`Char`** (`String.toCharArray()`), never from `String.toNumber()`. All symbols used here
(`toCharArray`, `toNumber`, `substring`, `length`) are present in
`~/.Garmin/ConnectIQ/Devices/venu2s/venu2s.api.debug.xml` — verified.

```monkeyc
    // Percent-encode a string for use in a URL query (RFC 3986).
    //
    // Characters MUST come from toCharArray(): on a 1-character STRING,
    // toNumber() parses a number ("5".toNumber() == 5) and returns null for
    // anything else - so "/".toNumber() was null, fell back to 0, and this
    // function emitted "%00" (NUL) for every reserved character. The whole
    // workout payload then lost its "|" and ";" separators in flight and the
    // backend rejected it with 422. Char.toNumber() gives the code point.
    function urlEncode(s as String) as String {
        var hex = "0123456789ABCDEF";
        var out = "";
        var chars = s.toCharArray();
        for (var i = 0; i < chars.size(); i++) {
            var v = (chars[i] as Char).toNumber();
            var unreserved = (v >= 0x41 and v <= 0x5A) or    // A-Z
                             (v >= 0x61 and v <= 0x7A) or    // a-z
                             (v >= 0x30 and v <= 0x39) or    // 0-9
                             v == 0x2D or v == 0x5F or       // - _
                             v == 0x2E or v == 0x7E;         // . ~
            if (v < 0 or v > 0xFF) {
                // Not a byte (the plan and exercise names are ASCII); never emit
                // a stray "%" that would truncate the query.
                out += "_";
            } else if (unreserved) {
                out += s.substring(i, i + 1);
            } else {
                var hi = (v / 16) % 16;
                var lo = v % 16;
                out += "%" + hex.substring(hi, hi + 1) + hex.substring(lo, lo + 1);
            }
        }
        return out;
    }
```

Hand-check before you move on (these are the exact characters in the real payload):

| input char | code | expected output |
|---|---|---|
| `|` | 0x7C | `%7C` |
| `;` | 0x3B | `%3B` |
| `/` | 0x2F | `%2F` |
| `,` | 0x2C | `%2C` |
| ` ` | 0x20 | `%20` |
| `-` | 0x2D | `-` (passes through) |
| `5` | 0x35 | `5` |
| none of the above may ever produce `%00` | | |

**Acceptance:** `grep -n "toNumber" embedded/monkeyc/source/Comms.mc` shows no `String.toNumber()`
inside `urlEncode`; the build in Task 9 succeeds.

## Task 4 — Honest workout duration

**File:** `embedded/monkeyc/source/Workout.mc`

- add `import Toybox.Time;`, a field `private var _startedAt;` (0 = unknown), init it in
  `initialize()`.
- `startWorkout()`: `_startedAt = Time.now().value();` (and keep `_sessionMs` only if something still
  reads it — grep first; `elapsedMs()` is the only reader).
- `save()`: persist `Application.Storage.setValue("lift_started_at", _startedAt);` and delete it in
  `clearSaved()`; `restore()` reads it back (leave it 0 if absent).
- `elapsedMs()`:

```monkeyc
    // Wall-clock, not System.getTimer(): the timer counts from BOOT, so a session
    // restored after a restart used to report the device uptime as its duration
    // (a 45-minute workout was recorded as 27138s). Clamped so a bad clock can
    // never write an absurd number into the training record.
    function elapsedMs() as Number {
        if (!_started or _startedAt <= 0) { return 0; }
        var d = Time.now().value() - _startedAt;
        if (d < 0 or d > 21600) { return 0; }
        return d * 1000;
    }
```

## Task 8 — Correct `week` / `dayInWeek` in the uploaded record

**File:** `embedded/monkeyc/source/Workout.mc`

```monkeyc
    // "Week 3" -> 3. The day list spans every week-block, so the index into it is
    // NOT the day of the week: a Week-3 day used to be uploaded as week 1,
    // dayInWeek 15 and landed in the wrong slot in Liftosaur.
    function weekNumber() as Number {
        var d = currentDay();
        if (d == null) { return 1; }
        var sec = d[:section] as String;
        var n = _trailingNumber(sec);        // parse the digits in "Week 3"
        return n > 0 ? n : 1;
    }

    function dayInWeek() as Number {
        var d = currentDay();
        if (d == null) { return 1; }
        var n = _trailingNumber(d[:name] as String);   // "Day 4" -> 4
        return n > 0 ? n : 1;
    }
```

`_trailingNumber` = a small private helper that scans for the last run of digits and returns it as a
Number (0 when there are none). Use `weekNumber()`/`dayInWeek()` in `buildWorkoutBody()` in place of
`:week => 1` and `_dayIndex + 1`. **Careful:** `loadPendingText()` already sets `:week => 1,
:day_in_week => 1` when rebuilding a stashed workout — leave that alone (a stashed workout has no day
context) but add a comment saying so.

Cross-check the parsed values for every day in `dist/plan.json` from
`tools/verify_watch_payload.py` (extend it: print `day -> week/dayInWeek`) and paste the table into
PROGRESS.md; the Week-1 days must all read week 1, Week 4 `Deload` days must read 4.
