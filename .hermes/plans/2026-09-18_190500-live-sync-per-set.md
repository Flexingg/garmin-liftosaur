# Live sync: push each completed set to Liftosaur as the workout happens

**Goal:** after each completed set, the watch pushes the workout-so-far to our backend, which writes it
straight into Liftosaur. The user watches the record grow in the Liftosaur phone app while training, and
a watch crash or a dead battery mid-session no longer loses the workout. If the phone is out of range
nothing changes: the existing end-of-workout post (and its stash/retry) remains the safety net.

**User's decisions (do not re-litigate):**
1. The record is **created on the first completed set**, then **updated after every set**.
2. **Discard deletes** the live record — nothing is left behind in Liftosaur.
3. **No new watch UI.** No "syncing…" line, no counters. Sync quietly; failures must be invisible and
   must never interrupt a workout.

**Liftosaur write API (verified against the MCP tool schemas — do not guess):**
- `create_history_record` → `{"text": <Liftohistory text>}` → returns the created record (parse its `id`)
- `update_history_record` → `{"id": <record id as STRING>, "text": <full replacement text>}`
- `delete_history_record` → `{"id": <record id as STRING>}`
- The backend reaches these through `app.plan.mcp_call(name, arguments)`; `create_history_record` is
  already used and its response is validated for an `id` (`watch_api.watch_workout`). **Follow that
  exact pattern for the other two** (a rejected write must never be reported as success).

## Task 1 — Backend: a live endpoint that creates then updates one record

**File:** `backend/python/app/watch_api.py` (+ `backend/python/app/plan.py` only if a helper is needed)

**1a. Accept a session start time in the compact payload.** `parse_compact()` currently reads
`day|section|program|duration_s;exercise|weight|reps|amrap;...`. Extend the header to an **optional 5th
field**, `started_at` (unix seconds, the watch's wall clock when the workout began), while keeping
4-field payloads parsing exactly as today (the stash on existing watches still sends 4):

```
Day 1|Week 1|5/3/1 BBB - Squat/Bench/Deadlift/OHP|2712|1789724800;Squat|220|5|0;...
```

**1b. A stable timestamp.** `to_liftohistory(w, plan=None)` stamps the record with `now()` unless
`finished_at` is set, which would make every update re-date the record. Make the stamp explicit:
`to_liftohistory(w, plan=None, stamp=None)` where `stamp` (unix seconds) overrides `w.finished_at`/now.
The live path passes, in order of preference:
1. `started_at` from the payload (stateless, stable across a backend restart) — **this is the primary**;
2. an in-memory `{record_id: stamp}` remembered when the record was created;
3. `now()` as a last resort.
Document in the docstring that (3) can shift a record's date once if the service restarted and the watch
sent no `started_at`.

**1c. The endpoint.**

```python
@router.post("/watch/workout/live")
async def watch_workout_live(payload: str | None = None, record: str = "", dry_run: int = 0) -> dict:
```

- parse the payload like the existing endpoint (same 422 semantics for a malformed header / no sets);
- render the text with the stable stamp;
- `dry_run=1` → return `{"recorded": False, "dry_run": True, "id": record or "dry", "sets": n,
  "liftohistory": text}` and **never** call Liftosaur;
- `record` empty → `create_history_record` → return `{"id": <new id>, "created": True, "sets": n}`;
- `record` set → `update_history_record({"id": record, "text": text})` → return
  `{"id": record, "updated": True, "sets": n}`. **If that update reports the record is gone** (Liftosaur
  rejects it / returns no id), fall back to creating a fresh record and return `created: True` with the
  new id — the watch stores whatever id comes back;
- **never shrink a live record:** keep an in-memory `{record_id: last_set_count}`; if a payload arrives
  with FEWER sets than the last one applied for that record (a late/out-of-order request), do not write
  and return `{"id": record, "skipped": "stale", "sets": n}`. This protects against an out-of-order POST
  silently dropping the user's last sets.

## Task 2 — Backend: a discard endpoint

```python
@router.post("/watch/workout/discard")
async def watch_workout_discard(record: str = "", dry_run: int = 0) -> dict:
```

- `dry_run=1` → `{"deleted": False, "dry_run": True, "id": record}` without touching Liftosaur;
- empty `record` → `{"deleted": False, "reason": "no record"}` (never an error: a discard with nothing
  synced is normal);
- otherwise `delete_history_record({"id": record})` → `{"deleted": True, "id": record}`; a "not found"
  reply is a success for our purposes (the user's intent was "nothing left behind") — say so in the
  response (`"reason": "already gone"`) rather than 502.

## Task 3 — Watch: push each set, remember the record id

**Files:** `embedded/monkeyc/source/Comms.mc`, `embedded/monkeyc/source/Workout.mc`

**3a. Storage.** Two keys: `lift_live_record` (the record id as a String; absent = not created yet) and
`lift_pending_record` (the id that a stashed end-of-workout post must UPDATE rather than duplicate).
Clear both in `clearSaved()`.

**3b. Payload.** Add `function livePayload() as String or Null` to `WorkoutController` — the same
compact string as `pendingText()` but with the 5th header field `_startedAt` (the wall-clock start
already tracked for the FIT work). Keep `pendingText()`/`loadPendingText()` working for the stash
(4-field = still valid; sending 5 is fine, the 4 fields stay in place).

**3c. `Comms.postLiveSet()`** — call it from `completeSet()` immediately after the set is logged and
`markLap()` has run. Requirements:

- **one request in flight at a time.** If a post is in flight, set a queued flag and return; when the
  response lands, if the flag is set, post the current (longer) payload. Without this, a late-arriving
  shorter payload could overwrite the record with fewer sets;
- URL: `LIFT_BACKEND + "/api/v1/watch/workout/live?payload=" + urlEncode(payload) + "&record=" + recordId`
  — query string only, no body (the body path is the one that crashed on this device; see `docs/06`);
- `recordId` comes from `Application.Storage.getValue("lift_live_record")` ("" when absent);
- on 2xx: store the returned `id` under `lift_live_record`; clear the in-flight flag; process the queue;
- on any failure: clear the in-flight flag, log it with `System.println`, set no user-visible state, and
  **do not stash a partial payload** — the end-of-workout post carries the complete set list anyway.
  A failed live sync must be invisible to the user (his decision #3).

**3d. `resolveSave()` integration.**
- **Save:** pass the live record id into the existing `postWorkout()` so the backend UPDATES that record
  instead of creating a second one. If no id is stored, behaviour is exactly today's (create). Then
  clear `lift_live_record`.
- **Discard:** call `Comms.discardLive()` → POST `/api/v1/watch/workout/discard?record=<id>`; clear the
  stored id whatever the result (the workout is being thrown away; a leftover record must not be
  updated later).
**3e. The stash must not duplicate.** `stashPending()` additionally stores the live record id under
`lift_pending_record`, and `retryPending()` sends it, so a retried end-of-workout post updates the same
record rather than creating a second one for the same session.

## Acceptance criteria

1. Logging a set creates the record; each later set updates that same record; Save updates rather than
   duplicating; Discard deletes.
2. Any live failure is invisible and never blocks or delays the workout, and the end-of-workout post (with
   its existing stash/retry) still saves everything.
3. Out-of-order or shorter payloads can never shrink a live record.
4. The timestamp of a live record stays fixed at the session start.
5. Backend suite ≥ 54 passed with nothing removed; the `venu2s` build is clean; `dist/` refreshed; no
   writes to the user's training history by the agent.

## Risks / open questions

- **Phone out of range** (a basement gym) is the normal failure case: live sync silently does nothing and
  the workout is still saved at the end. That is by design, not a bug.
- **Last-write-wins** if the user edits the same record in the Liftosaur app mid-workout.
- Live updates cost one small request per set (~20-30 per workout). If Liftosaur rate-limits or the phone
  relay stalls, the in-flight guard means requests simply queue at one at a time — it must never block
  the workout UI.
- The record is a *completed-looking* workout while still in progress, because Liftosaur has no
  "in progress" state we can set. The user has seen this and accepts it.
